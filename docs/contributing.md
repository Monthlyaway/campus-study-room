# 贡献与文档维护

[文档首页](README.md) · [开发导航](development/README.md) · [Agent 规则](../AGENTS.md)

这份流程同时面向人类开发者和协作 Agent。业务规格、权限与资源一致性约束共同适用；AI 评审不能记作真实人员签字。

## 一次改动如何完成

1. 从 [PRD](../01_PRD.md)、[规格导读](reference/README.md)和相关模块确定需求编号与受影响角色。先查看工作区，不覆盖已有未提交工作。
2. 把变更范围分给明确负责人。共享接口、schema、安全或资源锁改动需相关调用方共同评审；模块归属见 [ADR 0001](adr/0001-module-and-shared-layer-ownership.md)。
3. 修改实现及相应契约、生成客户端、迁移和文档。已部署迁移不重写；运行账号不获得 DDL 权限；不直接改 core 表来修复维修同步。
4. 开发阶段按[测试指南](development/testing.md)只做本次改动必要的针对性验证或缺陷复现，然后提交 PR。完整 `./scripts/check`、真实 PG/HTTP/SMTP 集成和发布浏览器 E2E 交给 codex-lb 上的 GitHub Actions，不在 Mac 或服务器开发目录预先重复整套检查；定位具体 CI 失败或用户明确要求时再做针对性复现。快检 `--unit-only` 不代表完整验收，合入仍须核对最新 SHA 的完整 CI 成功。实际执行、取消与尚未验证的范围分别记录。
5. 复核差异、生成漂移、链接、敏感内容和输出。只暂存本次文件，使用 Conventional Commits；正文写任务/需求编号与原因，一个逻辑改动一笔提交，不冒充其他模型或人类署名。
6. 在 codex-lb 的工作分支提交并通过 GitHub PR 合入 main。核对最新 SHA 的完整 CI，使用 rebase merge、默认不 squash。需要更新基线时先 rebase 再验证，不重写 main 历史。专用 runner、同机资源与套餐限制见[GitHub 工作流](operations/github.md)，不能为让检查变绿放宽可信代码边界或跳过 job。

当前用户已授权本项目在 codex-lb 自主开发、提交、发版、生产上线及最终 PR 合并；操作依据与配置边界见[当前交付 ADR](adr/0004-github-codex-lb-production.md)。不伪造第二位人工审批人，未提供的外部 SMTP 不得报告真实收信已验。

## 文档写给需要完成任务的人

每份指南先说读者能完成什么，再写前置条件、步骤、成功后看见什么、失败去哪里处理。用户手册使用界面里的中文菜单和按钮，不用 API 名称代替用户操作；工程指南给真实的文件链接和命令，不只列一串类名。

| 内容变化 | 应同步的文档 |
| --- | --- |
| 菜单、按钮、表单、业务状态或用户可见错误 | [用户工作流](user-guide/workflows.md)、[页面说明](user-guide/pages.md)、[常见问题](user-guide/faq.md)、[前端指南](development/frontend.md) |
| 公开/内部 API、鉴权、分页、幂等、错误格式 | OpenAPI、生成客户端、[API 指南](development/api.md)、相关模块参考与契约/行为测试 |
| 组件职责、调用边界、事务、锁、数据关系、安全策略 | [架构指南](architecture/README.md)、模块参考；新的决策增加 ADR |
| 开发工具、启动方式、账号种子或测试入口 | [开发环境](development/local-setup.md)、[账号参考](development/demo-accounts.md)、[测试指南](development/testing.md) |
| 配置、安装、发布、备份、回退、CI/Runner | [运维手册](operations/README.md)与相应深度参考 |
| 实际交付或测试结果 | [进度](progress.md)、[需求追踪](requirements-traceability.md)、新的日期化证据 |

每项事实尽量只有一个主文档，其他角色指南使用链接。账号映射统一在 `development/demo-accounts.md`；安装命令详解在 `operations/installation.md`；协议通则在 `development/api.md`；模块页承担深层规则。新增文件同时接入文档首页或对应子索引，避免只能通过搜索找到。

## 区分现状、规格和历史

- 当前指南应准确描述当前源码；删除过期的“仍待验证”时态时，要有真实依据，不能顺便宣称尚未实现的功能已完成。
- 根目录三份规格保留需求/任务编号和原始约束，入口明确其基线性质及现状映射。新的用户决策通过 ADR 解释，不静默改弱业务要求。
- 已冻结的 `docs/evidence/` 报告保留字节、日期、版本和失败结果。新的验证新增报告；索引可更新，不把旧结果改标成新版本实测。
- 私有状态、基础设施密码/令牌、Cookie、CSRF、数据库、浏览器 storageState 不进入文档或截图。用户本轮明确授权的唯一例外是将课程验收的真实初始应用登录账号/密码提交到私有仓库的 `development/demo-accounts.md`，供本人和老师查阅；不包括数据库/服务/平台凭据，也不放宽普通CI日志与artifact限制。其他示例用占位参数或在服务器读取秘密文件，不把真实值放进命令历史。
- 本机实例端口和绝对路径放在[当前实例](operations/current-instance.md)，通用安装与开发指南说明默认值和覆盖方式。

## 文档变更如何验收

先查链接、锚点、代码/脚本路径、命令前置和页面名称，再从读者任务复评。链接全通只能证明能打开文件，不能证明能据此工作。

- 用户应能从 README 找到工作流，再找到每个页面的操作、状态和错误处理。
- 架构师应能解释组件、数据、信任与事务边界，并定位实现和验证。
- 前端工程师应能启动界面、定位真实路由、修改请求/样式、选择调试与测试方式。
- 后端工程师应能启动服务、完成 API 会话、定位业务实现、修改契约/迁移并选对测试。
- 运维工程师应能选对安装模式、定位配置、判断健康，并按照有前置/成功信号的步骤处理发布和故障。

本次五角色评审的建议、实施对应和复评记录见[文档重构记录](reviews/documentation-2026-10-23.md)。静态核对、按文档实际执行、历史证据引用三者要分别标明。
