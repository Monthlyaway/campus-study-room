## 已定位问题及修复验证

1. 内部机器凭证错误复用了用户 BCrypt cost 12，每次 repair→core HTTP 都执行高成本密码验证。真实 20 并发直连 core 对照中，无认证版本接口 p95=75.32 ms、有效内部认证 p95=1538.21 ms、错误密码 p95=2702.72 ms，支持该瓶颈定位，见 [前测](performance/20261022T123019Z-internal-auth-before.json)。修复使用单独的机器凭证认证管理器，对随机高熵机器 secret 和用户名的固定长度 SHA-256 指纹做 `MessageDigest.isEqual`，两项均执行、不短路；不缓存用户权限、不改变用户 BCrypt cost 12。内部路由仍仅经私有容器网络访问。
2. 教室列表逐行统计座位数：page size 1 为 13 条 SQL，size 20 为 32 条，其中座位 count 从 1 增至 20 次。改为按当前页批量读取建筑/校区和分组统计座位，保留数据库可见范围过滤、分页与总数；不加载完整表后在内存分页。真实 PostgreSQL `AdminPersistenceTest` 9/9 通过（含随后角色列表批量权限回归），包括 21 间新教室、交替有/无座位、size 1/20 查询数不随行数增长及字段准确性。机器认证单测 3/3 通过，包括有效/错误/空凭据和用户密码 cost 12。

首轮查询计划在主负载结束后执行 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`：预约历史页 5.09 ms、count 3.92 ms，可用座位页 0.42 ms、count 0.73 ms。历史查询有数据库用户条件、排序和 limit，当前索引对已完成历史的覆盖仍可优化；这不是首轮秒级延迟来源。SQL 次数、完整计划、每次 HTTP JSONL 和数据库采样保存在 `output/performance/20261022T123019Z/`；[文件摘要](performance/20261022T123019Z-artifacts.json)记录字节数与 SHA-256，便于归档校验。失败结果没有被后续运行覆盖。

### 补充审计：性能环境的版本标签差异

最终只读审计发现：上述性能环境的三个实际不可变镜像ID均与R3 manifest一致，web的静态`/version.json`也为R3，但core/repair版本接口返回`development / working-tree`。性能准备器只固化了镜像，没有把manifest版本值传入后端运行环境，导致使用基础Compose的默认值。因此本轮性能结果有R3镜像内容与源码身份支持，**不代表性能环境的三个版本API一致性通过**。这里不能与19282发布实例的三版本一致浏览器验收混为一谈。

该差异不回填到既有`20261022T162929Z`结果或SHA清单；原始观测继续保留。两个版本属性在已检查的后端源码中用于版本响应，未见业务逻辑依赖；保留既有负载数值，同时明确运行标签配置存在缺口。

性能测试基础设施现已修正：准备/刷新时把manifest版本写进持久Compose override，后续repair重启仍使用同一值；共用启动前检查同时采集三个版本端点，发行模式不匹配即失败，开发诊断模式只记录实际版本而不强求静态Web标签一致。5项隔离单元回归通过，涵盖外部环境变量污染、三端点任一releaseId/commit不匹配、端点不可用和开发模式；测试没有调用实际Docker或HTTP。此次没有重启性能服务、修改当前运行配置或重跑负载。修复后标签的真实运行核验另行记录，不能把单元测试当作已有性能环境已修正。
