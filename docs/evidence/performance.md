# 性能验收证据（T50-03）

2026-10-22，按 PRD §12 与技术方案 §10.3 的完整数据规模、时长和阈值执行。**首轮失败后，修复镜像已通过第二轮完整性能验收。** 两轮都执行 60 秒预热及 300 秒持续负载，失败原始结果保留。当前结果绑定 development 镜像 ID；正式 release 仍需以最终 manifest 对应镜像复验。

## 环境与方法

独立 Docker Compose 项目 `studyroom-performance`，独立 PostgreSQL 数据卷及 `.local/performance` secret/control 目录，入口端口 19080。没有访问 local/test 业务数据库。真实数据：1000 账号、20 教室、1000 座位、100000 条 COMPLETED 历史预约，另有 100000 条已释放占用、历史审计/通知与 200000 条已完成任务。

常驻 PostgreSQL/core/repair/web/mailpit **共同限制在 CPU 0–3**，内存分别 3/2/2/0.5/0.5 GiB，总上限 8 GiB；每个容器的 swap 上限等于内存上限。实际 `docker inspect` 限额见 [容器记录](performance/20261022T123019Z-actual-container-limits.json)。迁移容器在测量前退出。Docker Desktop LinuxKit aarch64，Docker 28.5.2、kernel 6.12.54-linuxkit；Docker VM 共 10 vCPU、8217448448 字节内存（约 7.65 GiB，实际内存更紧）。应用限额满足共享四个 CPU 的上限，但宿主与其他项目共享，不能等同独占物理服务器；测量期间协调停止 Maven、Docker 构建和重测试。Python 负载生成器在宿主运行，数据库采样发生在受限 PostgreSQL 容器内。

当前为 development 镜像诊断；实际镜像 SHA-256 见 [环境记录](performance/20261022T123019Z-environment.json)，不能把当时源码 HEAD 当作镜像精确构建提交。正式 release 需绑定 manifest/镜像 ID 后复验。

[复现脚本与完整说明](../../tests/performance/README.md)：20 个真实登录会话，每线程顺序循环可用座位、个人预约历史、教室详情、个人报修历史四种读，然后交替创建/取消预约。每用户使用不同教室的座位，测量正常写。预热 60 秒后统计 300 秒，不加思考时间；共 8705 个统计请求，80% 读、20% 写。冲突争抢在主窗口之外单测，避免用业务冲突替代正常写成功延迟。

## 已定位问题及修复验证

1. 内部机器凭证错误复用了用户 BCrypt cost 12，每次 repair→core HTTP 都执行高成本密码验证。真实 20 并发直连 core 对照中，无认证版本接口 p95=75.32 ms、有效内部认证 p95=1538.21 ms、错误密码 p95=2702.72 ms，支持该瓶颈定位，见 [前测](performance/20261022T123019Z-internal-auth-before.json)。修复使用单独的机器凭证认证管理器，对随机高熵机器 secret 和用户名的固定长度 SHA-256 指纹做 `MessageDigest.isEqual`，两项均执行、不短路；不缓存用户权限、不改变用户 BCrypt cost 12。内部路由仍仅经私有容器网络访问。
2. 教室列表逐行统计座位数：page size 1 为 13 条 SQL，size 20 为 32 条，其中座位 count 从 1 增至 20 次。改为按当前页批量读取建筑/校区和分组统计座位，保留数据库可见范围过滤、分页与总数；不加载完整表后在内存分页。真实 PostgreSQL `AdminPersistenceTest` 9/9 通过（含随后角色列表批量权限回归），包括 21 间新教室、交替有/无座位、size 1/20 查询数不随行数增长及字段准确性。机器认证单测 3/3 通过，包括有效/错误/空凭据和用户密码 cost 12。

首轮查询计划在主负载结束后执行 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`：预约历史页 5.09 ms、count 3.92 ms，可用座位页 0.42 ms、count 0.73 ms。历史查询有数据库用户条件、排序和 limit，当前索引对已完成历史的覆盖仍可优化；这不是首轮秒级延迟来源。SQL 次数、完整计划、每次 HTTP JSONL 和数据库采样保存在 `output/performance/20261022T123019Z/`；[文件摘要](performance/20261022T123019Z-artifacts.json)记录字节数与 SHA-256，便于归档校验。失败结果没有被后续运行覆盖。
